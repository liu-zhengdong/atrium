# server/tasks 约定

任务账本与执行者运行时。总体规范见根目录 `AGENTS.md`。

- 子目录：`ledger/` 账本、状态机与排期；`dispatch/` 派发（队列、挑执行者、工作区、拉起、捎话、接管与残留进程），工具适配器在 `adapters/`；`workers/` 执行者档案与专员；`logs/` 执行者日志读取与概括；`gates/` 验收关卡、交付事实与合入前审阅；`merge/` 合入队列、本地检查与上线；`watch/` 看门狗、持球与期限、临时错误与思考耗尽；`quota/` 额度；`events/` 事件与投递；`secretary/` 秘书会话与唤醒。顶层只留编排（`runner.ts`、`routes.ts`）与共用的 git / gh 调用。
- 判定与 IO 分开：状态转移（`state.ts`）、就绪（`schedule.ts`）、关卡（`gates.ts`、`delivery-gates.ts`）、看门狗（`watchdog.ts`）、临时错误与思考耗尽（`transient.ts`、`thinking.ts`）、额度信号（`quota-signal.ts`）都是纯函数，穷举测试；落库、拉进程、查 git/gh 放在各自的 `*-runtime.ts`、`facts.ts`、`spawn.ts`、`runner.ts`。
- 新执行者工具：在 `adapters/` 加一份 `Adapter`（数据 + 把提示词、工作目录、模型、强度变成进程调用的纯函数 `build`），登记到 `adapters/index.ts` 与 `TOOLS`；工具不支持的参数报错，不静默丢弃。
- 通用命令行执行者（t271）：`harness/<名字>` 写 `protocol: cli` 的不用写代码。档案写法解析在 `adapters/cli-spec.ts`（纯函数，毛病用档案键名说清楚），按模板拉起在 `adapters/cli.ts`，结局（`error_match`、`done_match`）在 `adapters/cli-outcome.ts`；登记表是 `adapters/index.ts` 的 `ADAPTERS`（内置不可盖），服务启动整批登记在 `custom-tools.ts`，改档案（`worker-profile-edit.ts`）与 `resolveWorker` 按名重登或撤下。`Tool` 因此是字符串：要列全部工具用 `toolNames()`，只认内置的用 `TOOLS` / `isBuiltinTool`。远程主机只上报内置工具，通用执行者只在本机跑。契约测试 `tests/worker-contract.ts`。
- 自定义模型端点（t271）：规则校验、取端点、密钥注入成哪个变量在 `endpoint.ts`（纯函数）；工具怎么接写在各自适配器（`endpoints` 声明能接的接口种类，`build` 按 `LaunchInput.endpoint` 传入），改档案时的工具检查在 `profile-tool-check.ts`；密钥与任务凭据同一条路注入（`taskSecretValues` 的 `extra`），不进 `Launch.env`（它会写进日志抬头）。
- 新关卡：在 `gates.ts` 加判定分支，只吃 `facts.ts` 收集的事实；档案 `checks` 引用它的名字。关卡结论与原因写进任务事件，不采信执行者自述。
- 执行者档案存数据库（`worker-profiles.ts`：`worker_profiles` 当前版、`worker_profile_revisions` 只增修订），`resolveWorker(标识, db)` 读库；三层叠加时以最具体的一层为准：`trust`、`max_risk`、`limits`、`checks` 写了就整项取这一层（能放宽，写空即撤销），`billing` 任一层 metered 即 metered；`checks` 里不认识的关卡名派活时忽略，解析档案时给警告。改档案走 `atrium workers edit`（`worker-profile-edit.ts` 校验），不直接写表。旧目录（`ATRIUM_WORKERS_DIR`，默认数据目录时缺省 `~/Atrium/workers`，隔离服务不读主目录）只在首次启动导入一次；测试用 `tests/profile-fixture.ts`。
- 执行者进程：经平台层拉起与结束（`server/platform/`：Unix 独立进程组，Windows 按进程树结束）、白名单环境（`worker-env.ts`，Windows 另放行系统变量）、输出直接写日志文件；服务重启不带走执行者，由 `recovery.ts` 按 pid 接管或判失败。
- 捎话（`task tell`）：判定在 `tell.ts`（送达方式、退出后续上/重派/收尾），账在 `tell-ledger.ts`（task_events kind=tell，送达后原地更新 detail），标准输入写端在 `live-input.ts`，续上与重派在 `tell-runtime.ts`；适配器用 `tell`、`resume`、`sessionOf` 声明能力。
- 合入前审阅（`review.ts` 判定、`review-runtime.ts` 编排）：状态只在 `tasks.delivery_stage='reviewing'` 与 `review_task`，巡检从账本续上；审阅结论只认审阅者摘要里最后一个「审阅结论：通过/打回」，打回走合入队列的 `handBack`。结论补答（`conclusion.ts` 判定、`conclusion-runtime.ts` 登记）：审阅者退出时读不出结论，登记一条运行时捎话，由 `followUpTells` 续上同一执行者补答，每轮一次。
- 事件先落库再投递；同一订阅者、同一去重键的未确认事件合并；订阅者自己发起的动作不投给他本人。事件级别（要处理/知会）写入 `task_inbox.level`，过滤在 SQL 里做（`events.ts`）；收件箱的保留上限在 `retention.ts`（已确认知会按时间/条数清），由运行时低频清理；任务事件不清理，交付事实（`delivery-records.ts`）直接从事件查，统计列由 `applyDeliveryEvent` 随事件增量维护。
- 测试用 `tests/task-fixture.ts` 的假执行者和临时目录，不依赖本机装了哪些 CLI 或 OpenQuota。
- 本机减负（#358）：限额读取与判定在 `host-load.ts`（纯函数，采样在 `HostLoad`）；闸门只在 `Executors.drain` 用，满了或太忙就留在队里；测试并发经 `worker-env.ts` 注入 `ATRIUM_TEST_CONCURRENCY`。太忙看两条线（t113）：Atrium 进程树占的核数（`server/platform/cpu-plan.ts` 判定、`cpu.ts` 按平台采样，巡检时刷新）与整机负载保护线。进程树含短命子进程与被收养的孤儿（t203）：怎么认 Atrium 拉起的进程在 `orphans.ts` 的 `recognizer`：Linux 读执行者带的 `ATRIUM_SPAWN` 标记（拉起时在 `Executors.spawnEnv` 加，巡检任务不加）；macOS 读不到进程环境，按被 1 号收养的进程的工作目录与启动时刻对任务工作树（执行者的 shell 各开进程组，不能按进程组认）；认不准就不认。任务结束 30 分钟后还活着的孤儿由 `OrphanReaper` 在巡检里结束。
- 优先级与派活队列：任务只有一个优先级（紧急 / 修复 / 普通 / 闲时），存 `tasks.prio`（旧库的 `urgent`、`priority`、`task_type`、`size` 等列留着不读不写，加列时折算一次；读出的视图只给 `priority`，见 `ledger-model.ts` 的 `RETIRED`）；写法、先后 `rank` / `rankSql` 在 `priority.ts`，缺省普通。想跑的任务一律进 `task_queue`：`TaskRunner.run` 与排期巡检只校验、挑执行者、入队，唯一拉起执行者的是 `Executors.drain`，按 `queue.ts pending`（优先级、入队先后）一件件挑主机；紧急只多一条：跳过本机负载限制（`hostGate` / `hostFit` 的 `urgent`）。合入队列 `NEXT_MERGE` 按同一个优先级排，串行、不抢占。清残留执行者进程（`host clean`，t217）：哪些算残留、认没认准在 `leftovers.ts`（纯函数），核对结束与 `cleanHost` 在 `leftovers-reap.ts`，远程经 `RemoteHosts.clean` 交那台的代理；结束的记进所属任务的 `leftover_killed` 事件。
- 任务详述（#355）：内容存 `tasks.brief`（校验与上限在 `brief.ts`），派活、审阅、`task show` 只读库里的内容；`brief_path` 只记来源。运行时自己生成的详述（审阅）用 `clipBrief` 截到上限再存。
- 持球人（#355）：未结束任务「球在谁手里」判定在 `holder.ts`（纯函数、穷举测试），事实在 `holder-facts.ts` 取；`top`、`task show` 与状态栏按它显示，不在命令行里另猜。一句话单行、至多 `HOLDER_WIDTH`；合入交回原因由 `mergeShort` 缩成「类别 + 一句」，原因全文只在单个任务视图的 `holder.detail` 给 `task show`。
- 远程执行者（#358 第 1 步）：主机账与判定在 `server/hosts/`（`state.ts` 纯函数：连接状态、`hostFit` / `chooseHost` 挑主机、远程目录布局、日志续传、重连对账），代理在 `server/agent/`。`Active.host` 有值的是远程运行：拉起走 `Executors.launchRemote`（`prepareRun` 给 site 时只算路径、写提示词），退出由代理上报（`RemoteHosts.exit` → `remoteExited`），结束进程走代理；收尾的 git 事实经 `RemoteHosts.exec` 在那台查，gh 仍在本机。独占工具、执行者上限、`inFlight` 按主机分开算；排队行 `task_queue.host_id` 钉住用户指定的主机。检查只在服务那台跑：合入队列 rebase 后在本机工作树跑 `runLocalCheck`（交付关卡不跑全量检查），进行中的「本地检查中」由 `holder.ts` 的 `checking` 给出。
- 检查没跑成（t204）：合入队列的检查结果分过／没过／没跑成（含检查命令找不到：`missingCommand`，`runLocalCheck` 据此记 infra），判定与重跑上限在 `check-outcome.ts`（纯函数），读基础分支的 `.agents/timing-sensitive` 在 `check-rerun.ts`；没跑成的放回队尾并暂停队列（`merge-runtime.ts` 的 `rerunLater`），用尽转卡住写「基础设施问题」；持球人的 `rerun` 由 `merge_check_rerun` 事件给出。
- 持球与期限：所有「卡住／没进展／没人管」收成一条规则。时限表 `DUE`、判定 `dueStep`、显示 `heldText`、事件内容 `overdueDetail` 在 `overdue.ts`（纯函数）；到期动作：执行者（启动 3 分钟、运行 20 分钟）由 `Executors.tick` 按 `watchdog.ts judge` 判卡死并结束进程树；检查（10 分钟没输出）由 `check-quiet-watch.ts` 的 `QuietWatch` 结束，`check-quiet.ts` 的 `stalledCheck` 按已查出的失败分类（卡住的只重跑 `MAX_STALL_RERUNS` 次）；leader 手里的受阻任务与等发版的由 `overdue-runtime.ts` 的 `patrolOverdue` 在运行时巡检里一分钟一轮（叫醒记任务事件 `overdue`，上交记 `escalated`）；秘书由 `secretary-fallback.ts` 按 `DUE.secretary`。统一发 `overdue` 事件（`holder`、`held_ms`、`step`、`next`；执行者、检查的是知会）。持球人带 `due`（哪一行、从何时起），状态栏与 top 句末同一种「N 分钟没动」；执行者的进展时刻来自服务内存（`Active.state.lastProgressAt`，经 `topRows` 的 `progress` 传入）。测试运行器的心跳在 `tests/still-running.ts`（判定）与 `still-running-reporter.ts`（挂在 `node --test` 上）。
- 合入串行：合入队列一次一件，rebase 到最新 main、重跑本地检查、按检查过的提交合入；读账在 `merge-ledger.ts`（上次 rebase 到哪个提交），git/gh 调用在 `merge-git.ts`。
- 上线：端到端验证由执行者交付前在隔离实例跑、贴进 PR，审阅核对（`review.ts` 清单）；自升级上线后 `online-runtime.ts` 的 `cliSmoke` 跑只读冒烟（`status`、`task ls`、`--help`），没过记 `online_failed`；`online` 是知会。
- 停止事件 `stop_requested` / `unqueued` 记发起者 `by`：`task stop` 记 `?as=`，`host clean` 记调用者并写 reason「host clean hN 止损」；`note` 只进事件，不改投递（`active.stop.by` 仍是 `task stop` 的订阅者）。
- 登记交付（t257，`task deliver`）：秘书、leader 亲自做完的活不经执行者关卡，登记 PR 与可选工作树后直接进合入队列。判定（能不能登记、PR 可不可收、合入用哪个工作树）是 `register-delivery.ts` 的纯函数，gh / git 取事实与落库在 `register-delivery-runtime.ts`；记 `delivery_registered` 事件，`MergeQueue.requeue` 把它当作关卡通过。没给工作树的由 `MergeQueue.process` 按工作树规则在本机另建（与远程任务同一条路），建好写回 `tasks.worktree`，之后照本机任务核对与清理。
- 秘书在不在听（t242）：`EventInbox.presence` 记此刻有没有连接挂着 wait（唤醒通道自己的 peek 用 `trackOnline: false`，不算）与最近一次在听的时刻；判定与显示在 `secretary-watch.ts`（纯函数：`watchDecision` 何时后台叫醒、叫不起来的原因，`secretaryText` 状态栏与 top 的一句）。后台兜底 `secretary-fallback.ts` 按它行事：没人听满 `DUE.secretary`（3 分钟）接着 `atrium chat` 开过的会话跑一轮，叫不起来经 `alert` 推到手机（`notify/model.ts` 的 `awayPush`，同一段只推一次），`TaskRunner.secretaryWatch` 把状态交给 `top`。
- 检查前装依赖（t252、t216）：`install-deps.ts` 判定（`depsPlan` 纯函数：有锁文件而没装、哈希记号对不上、执行者装的比锁文件旧）与 `installDeps`（`npm ci --prefer-offline`，输出接在检查日志前面、记用时），`runLocalCheck` 每次跑检查前调用；装失败时检查不跑，`LocalCheck.install.status=failed` 并记 `infra`，按 t204 归「没跑成」：合入队列放回队尾重跑。`checkDetail` 把装依赖写成事件的 `deps` 一句，`checkSummary` 附在「本地检查」一行末尾。
