# server/tasks 约定

任务账本与执行者运行时。总体规范见根目录 `AGENTS.md`。

- 判定与 IO 分开：状态转移（`state.ts`）、就绪（`schedule.ts`）、关卡（`gates.ts`、`delivery-gates.ts`）、看门狗（`watchdog.ts`）、临时错误与思考耗尽（`transient.ts`、`thinking.ts`）、额度信号（`quota-signal.ts`）都是纯函数，穷举测试；落库、拉进程、查 git/gh 放在各自的 `*-runtime.ts`、`facts.ts`、`spawn.ts`、`runner.ts`。
- 新执行者工具：在 `adapters/` 加一份 `Adapter`（数据 + 把提示词、工作目录、模型、强度变成进程调用的纯函数 `build`），登记到 `adapters/index.ts` 与 `TOOLS`；工具不支持的参数报错，不静默丢弃。
- 新关卡：在 `gates.ts` 加判定分支，只吃 `facts.ts` 收集的事实；档案 `checks` 引用它的名字。关卡结论与原因写进任务事件，不采信执行者自述。
- 执行者档案存数据库（`worker-profiles.ts`：`worker_profiles` 当前版、`worker_profile_revisions` 只增修订），`resolveWorker(标识, db)` 读库；三层叠加时以最具体的一层为准：`trust`、`max_risk`、`limits`、`checks` 写了就整项取这一层（能放宽，写空即撤销），`billing` 任一层 metered 即 metered；`checks` 里不认识的关卡名派活时忽略，解析档案时给警告。改档案走 `atrium workers edit`（`worker-profile-edit.ts` 校验），不直接写表。旧目录（`ATRIUM_WORKERS_DIR`，默认数据目录时缺省 `~/Atrium/workers`，隔离服务不读主目录）只在首次启动导入一次；测试用 `tests/profile-fixture.ts`。
- 执行者进程：经平台层拉起与结束（`server/platform/`：Unix 独立进程组，Windows 按进程树结束）、白名单环境（`worker-env.ts`，Windows 另放行系统变量）、输出直接写日志文件；服务重启不带走执行者，由 `recovery.ts` 按 pid 接管或判失败。
- 捎话（`task tell`）：判定在 `tell.ts`（送达方式、退出后续上/重派/收尾），账在 `tell-ledger.ts`（task_events kind=tell，送达后原地更新 detail），标准输入写端在 `live-input.ts`，续上与重派在 `tell-runtime.ts`；适配器用 `tell`、`resume`、`sessionOf` 声明能力。
- 请专员（#322）：账在 `concerns.ts`（task_concerns，一位专员一行、本轮审查任务与结论），判定在 `concern-gate.ts`（审查结论、专员关卡合成、`invite_when` 提示、提示词段落），执行在 `concern-runtime.ts`（其余关卡通过后建审查子任务、审查不再跑后记结论并补判父任务；否决或没出结论的留在受阻交负责的 leader 判断，不认同用 `task merge` 放行，见 `overruleConcerns`）；审查任务自己的结局不单独投递。
- 合入前审阅（`review.ts` 判定、`review-runtime.ts` 编排）：状态只在 `tasks.delivery_stage='reviewing'` 与 `review_task`，巡检从账本续上；审阅结论只认审阅者摘要里最后一个「审阅结论：通过/打回」，打回走合入队列的 `handBack`。结论补答（`conclusion.ts` 判定、`conclusion-runtime.ts` 登记）：审阅、专员审查、会审意见与汇总退出时读不出结论，登记一条运行时捎话，由 `followUpTells` 续上同一执行者补答，每轮一次。专员关卡在前、审阅在后：专员都通过后同样经 `review.admit` 分档。
- 会审（#322）：账在 `councils.ts`（task_councils 议题一行、council_members 每位专员一个意见任务），判定在 `council-gate.ts`（意见立场、汇总解析、结局合成、提示词），编排在 `council-runtime.ts`（意见收齐交 leader 汇总、汇总完成记结论）；议题任务自己的执行者运行就是汇总，意见任务与汇总的完成不单独投递，结局投 `council_decided` / `council_escalated`。议题任务取消时会审转「已关闭」（`council-close.ts`，状态转移同一事务里关；巡检补关老库里卡住的），推进按议题分页走完全部未定会审，不被卡住的挤掉。
- 事件先落库再投递；同一订阅者、同一去重键的未确认事件合并；订阅者自己发起的动作不投给他本人。事件级别（要处理/知会）写入 `task_inbox.level`，过滤在 SQL 里做（`events.ts`）；两张表的保留上限在 `retention.ts`（已确认知会按时间/条数清，已结束任务的旧事件留最近一段与最新交付窗口，并保留 `created` 与每个任务最新一条 `note`——全景图取派发人与最新备注要用；删旧交付窗口的事件前先把交付事实固化进 `task_deliveries.facts`，交付统计不受影响），由运行时低频清理。
- 测试用 `tests/task-fixture.ts` 的假执行者和临时目录，不依赖本机装了哪些 CLI 或 OpenQuota。
- 本机减负（#358）：限额读取与判定在 `host-load.ts`（纯函数，采样在 `HostLoad`）；`TaskRunner.run` 与 `Executors.drain` 拉起前过同一道闸门，满了或太忙落库排队、巡检时按入队顺序拉起；本地检查并发由共享的 `sharedLocalChecks` 上限控制；测试并发经 `worker-env.ts` 注入 `ATRIUM_TEST_CONCURRENCY`。太忙看两条线（t113）：Atrium 进程树占的核数（`server/platform/cpu-plan.ts` 判定、`cpu.ts` 按平台采样，巡检时刷新）与整机负载保护线。进程树含短命子进程与被收养的孤儿（t203）：怎么认 Atrium 拉起的进程在 `orphans.ts` 的 `recognizer`：Linux 读执行者带的 `ATRIUM_SPAWN` 标记（拉起时在 `Executors.spawnEnv` 加，巡检任务不加）；macOS 读不到进程环境，按被 1 号收养的进程的工作目录与启动时刻对任务工作树（执行者的 shell 各开进程组，不能按进程组认）；认不准就不认。任务结束 30 分钟后还活着的孤儿由 `OrphanReaper` 在巡检里结束。
- 紧急（t113、t215 紧急通道）：只认 `tasks.urgent`；判定都在 `urgent.ts`（谁能标 `markVerdict`、止损写法 `parseStopgap`、抢占选谁 `preemptPlan`、何时续上 `resumePlan`、合入暂停与让路 `mergeDecision` / `mergeYield`、换人时机 `swapDue`、挑人先后 `urgentOrder`、阶段推送 `urgentStage`），账在 `urgent-ledger.ts`（tasks 的 urgent_why / urgent_by / avoid_hosts / stopgap 列，`task_preemptions`、`task_after_reviews`），执行在 `urgent-runtime.ts`（止损、腾位置、续上）与各运行时：`Executors.pause` / `slots` / 收尾的 `paused` / `swapped`、`MergeQueue.next` / `halted`、`ReviewGate.stepAfter`、`planOnline` 的 `urgentBusy`；阶段推送 `notice.ts publishUrgentStage`。闸门（`hostGate` 的 `urgent`）、排队先后（`queueOrder`，执行者队列 `queueHeads` 与合入队列 `NEXT_MERGE` 同一规则）、本地检查排位（`checkPlacement`）在 `host-load.ts`；额度保留、trust / max_risk、依赖不因紧急放宽。清残留执行者进程（`host clean` 与止损，t217）：哪些算残留、认没认准在 `leftovers.ts`（纯函数：账本里不在跑、一天内结束的 pid，命令行是那个工具、启动时刻落在任务建立与结束之间），本机与代理共用 `leftovers-reap.ts` 核对并用平台层 `killTree` 整树结束，远程经 `RemoteHosts.clean` 交那台的代理；结束的记进所属任务的 `leftover_killed` 事件。
- 闲时（t136）：只认 `tasks.priority`（normal / idle），建任务时按归属部分缺省（管方面的部分或其下为 idle，`priority.ts` 的 `aspectPart`）；判定（档位、先后 `rank`、闲时能不能派 `idleAhead` / `idleAheadAll`）是 `priority.ts` 的纯函数。派发三处同一规则：`TaskRunner.run`（前面有普通任务在等同一类执行者就排队）、`Executors.drain`（队首紧急 → 普通 → 闲时，闲时的再看 `idleAhead`）、`Scheduler.tick`（同一轮先派普通、闲时的最后）。只改排序，不改关卡；合入队列与本地检查不看闲时。
- 任务详述（#355）：内容存 `tasks.brief`（校验与上限在 `brief.ts`），派活、审阅、会审、`task show` 只读库里的内容；`brief_path` 只记来源。运行时自己生成的详述（审阅、专员审查、会审意见与汇总）用 `clipBrief` 截到上限再存。
- 持球人（#355）：未结束任务「球在谁手里」判定在 `holder.ts`（纯函数、穷举测试），事实在 `holder-facts.ts` 取；`top`、`task show` 与状态栏按它显示，不在命令行里另猜。一句话单行、至多 `HOLDER_WIDTH`；合入交回原因由 `mergeShort` 缩成「类别 + 一句」，原因全文只在单个任务视图的 `holder.detail` 给 `task show`。
- 横跨部分（#373）：管方面的部分与要点适用范围在 `server/org/aspects.ts`（`appliedFrom`、`covers` 纯函数）；任务牵涉的部分账在 `also.ts`（task_also 只存显式 `--also`，自动牵涉每次按要点算）；专员归属与可选范围在 `specialist-scope.ts`（`scopeOf`、`inScope` 纯函数），`--by`/`--ask` 校验、`task pick`、`specialist ls --part` 共用；牵涉知会 `publishInvolved`（notice.ts，info 级不叫醒），被牵涉部分的 leader 只能记备注与捎话（leaders/scope.ts `remarkVerdict`）。
- 远程执行者（#358 第 1 步）：主机账与判定在 `server/hosts/`（`state.ts` 纯函数：连接状态、`hostFit` / `chooseHost` 挑主机、远程目录布局、日志续传、重连对账），代理在 `server/agent/`。`Active.host` 有值的是远程运行：拉起走 `Executors.launchRemote`（`prepareRun` 给 site 时只算路径、写提示词），退出由代理上报（`RemoteHosts.exit` → `remoteExited`），结束进程走代理；收尾的 git 事实经 `RemoteHosts.exec` 在那台查，gh 仍在本机。独占工具、执行者上限、`inFlight` 按主机分开算；排队行 `task_queue.host_id` 钉住用户指定的主机。第 2 步：合入队列 rebase 后的检查经 `server/hosts/check-runtime.ts` 的 `CheckDispatch` 挑主机跑（`MergeQueue` 的 `checks` 选项；交付关卡不跑全量检查，`local_check` 只写明由合入队列跑），结果事件带 `host` 与 `commit`，进行中的「在 hN 上跑检查」由 `holder.ts` 的 `checking` 给出。
- 检查没跑成（t204）：合入队列的检查结果分过／没过／没跑成（含检查命令找不到：`missingCommand`，`runLocalCheck` 据此记 infra），判定与重跑上限在 `check-outcome.ts`（纯函数），读基础分支的 `.agents/timing-sensitive` 在 `check-rerun.ts`；没跑成的放回队尾并暂停队列（`merge-runtime.ts` 的 `rerunLater`），用尽转卡住写「基础设施问题」；持球人的 `rerun` 由 `merge_check_rerun` 事件给出。
- 上线后验证（t181）：判定在 `verify.ts`（纯函数：执行者配置、详述与硬规矩、`verify.json` 合成结论、写进事件前 `scrub` 截断并抹凭据），账与执行在 `verify-runtime.ts`（task_verifications 一个验证任务一行；`openVerify` 在「已上线」同一事务里建子任务，建不起来用 SAVEPOINT 只回滚自己；`settleVerifications` 从未出结论的行驱动、一条 SQL 取齐状态与汇报，结论记原任务事件 `verified`）。验证任务的结局不单独投递；拉起时去掉 `ATRIUM_WORKER`、带 `ATRIUM_VERIFIER=1` 与 `ATRIUM_QUOTA_READERS=off`（`Executors.runEnv`），只在本机跑，提示词只附验证步骤、岗位说明与硬规矩。验证之后（t182）：通过就结束；没通过、无法验证由 `TaskRunner.verified` 经 `publishTask` 投 `verify_failed` / `verify_unverifiable`（内容 `verifyEventDetail`，去重键 `tN:verify`）；派了验证任务的 `online` 是知会（`event-level.ts` 的 `isVerifiedOnline`，老行在 `ensureEventTables` 回写）。显示的判定在 `verify-view.ts`（命令行静态引入，不引重模块），`verifyViews` 一批任务两条 SQL 取齐状态与收件箱里投给了谁；`top` 取行多列验证中与 24 小时内没过的原任务（`VERIFY_TOP_SQL`，各走部分索引）。
- 验证执行者的服务端边界（t239）：判定在 `verify-scope.ts`（纯函数：路由 → 是不是止损类操作），校验在 `verify-guard.ts`（preHandler，认 `x-atrium-verifier` 头，值是验证任务 tN）。命令行在 `ATRIUM_VERIFIER=1` 且连的是运行时给的真实服务（`ATRIUM_VERIFIER_DATA`）时带这个头；验证执行者自己起的隔离实例不带、不受限。停止事件 `stop_requested` / `unqueued` 记发起者 `by`：`task stop` 记 `?as=`（验证执行者停自己记 tN），`host clean` 记调用者并写 reason「host clean hN 止损」，紧急任务止损记那件紧急任务；`note` 只进事件，不改投递（`active.stop.by` 仍是 `task stop` 的订阅者）。
